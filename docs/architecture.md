# Архитектура системы

## 1. Выбранный подход

Для учебной версии предлагается **модульный монолит** на C# / ASP.NET Core Web API. Модули имеют отдельные ответственности, но запускаются в одном приложении. Такой вариант снижает сложность развертывания и позволяет показать взаимодействие модулей через явные контракты без преждевременного введения сетевой инфраструктуры микросервисов.

## 2. Схема компонентов

```text
                HTTP-клиент / Swagger
                         |
                         v
                 +----------------+
                 |    ApiHost     |
                 | ASP.NET Core   |
                 +--------+-------+
                          |
           +--------------+----------------+
           |              |                |
           v              v                v
 +----------------+ +--------------+ +----------------+
 | CustomerModule | | VehicleModule| |ServiceOrder    |
 |                | |              | |Module          |
 +----------------+ +--------------+ +-------+--------+
                                              |
                                +-------------+-------------+
                                |                           |
                                v                           v
                         +-------------+             +-------------+
                         | WorkModule  |             | PartsModule |
                         +------+------+             +------+------+
                                |                           |
                                +-------------+-------------+
                                              v
                                      +---------------+
                                      | PricingModule |
                                      +---------------+

      Публичные DTO и запросы/ответы: Contracts
      Хранение данных: EF Core / SQLite (предлагается)
```

## 3. Слои

- **API** — HTTP-маршруты, валидация формата запросов, перевод результата в HTTP-ответ.
- **Application/Modules** — сценарии использования и координация модулей.
- **Domain** — сущности и бизнес-правила: расчет стоимости, проверки количества, допустимые переходы статусов.
- **Infrastructure** — реализация доступа к данным через Entity Framework Core и SQLite.
- **Contracts** — DTO, предназначенные для обмена между API и прикладными модулями.

Названия физических проектов могут быть скорректированы при создании решения, но ответственность слоев должна оставаться ясной.

## 4. Принципы

1. Зависимости направлены к абстракциям и публичным контрактам, а не к внутренним классам соседнего модуля.
2. Денежные вычисления выполняются через `decimal`.
3. Идентификаторы сущностей — `Guid`.
4. Асинхронные операции ввода-вывода принимают `CancellationToken`.
5. Ошибки бизнес-правил имеют стабильный код, пригодный для тестов и API-ответов.
6. Смена статуса и изменение строк заказа должны проверяться бизнес-правилами, а не только интерфейсом.

## 5. Поток создания заказа

```text
HTTP POST /api/service-orders
             |
             v
ApiHost: проверка формата
             |
             v
ServiceOrderModule
   |         |
   |         +--> VehicleModule: проверить автомобиль
   +------------> CustomerModule: проверить клиента/владельца
             |
             v
Создать заказ со статусом Created
             |
             v
Вернуть ServiceOrderDto
```

## 6. Ограничения решения

На этапе 1 это проектная схема, а не доказательство уже работающего приложения. Конкретная схема БД, DI-регистрация и конечные маршруты будут подтверждены при реализации и интеграционных тестах.
