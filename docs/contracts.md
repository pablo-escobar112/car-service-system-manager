# Контракты и протоколы взаимодействия

## 1. Общие правила

- Внутренние вызовы модулей выполняются через интерфейсы C# и DI; транспорт — вызов метода внутри одного процесса.
- Внешний клиент обращается к `ApiHost` по HTTP/JSON.
- Идентификаторы передаются как GUID.
- Денежные значения — `decimal`.
- Даты без времени, например дата создания заказа, представлены ISO 8601 (`YYYY-MM-DD`).
- Все асинхронные методы, способные ожидать I/O, принимают `CancellationToken`.
- Ошибки возвращаются со стабильным `errorCode` и человекочитаемым сообщением. Точные HTTP-коды закрепляются при реализации API.
- Версия внутренних контрактов на данном этапе: `v1`.

## 2. Протокол №1: создание заказа обслуживания

### Инициатор и получатель
Инициатор — `ApiHost`; получатель — прикладной сервис `ServiceOrderModule`.

### Назначение
Создать заказ для зарегистрированного клиента и автомобиля.

### Механизм и точка входа
HTTP `POST /api/service-orders`, JSON. Внутри приложения вызывается `IServiceOrderService.CreateAsync(CreateServiceOrderRequest, CancellationToken)`.

### Запрос

```json
{
  "customerId": "7b6e41e8-2d8b-4d83-8c90-a2d1b0b0c100",
  "vehicleId": "7b6e41e8-2d8b-4d83-8c90-a2d1b0b0c101",
  "problemDescription": "Проверить тормозную систему",
  "createdAt": "2026-10-27"
}
```

### Успешный ответ
HTTP `201 Created` и объект `ServiceOrderDto`:

```json
{
  "id": "7b6e41e8-2d8b-4d83-8c90-a2d1b0b0c102",
  "customerId": "7b6e41e8-2d8b-4d83-8c90-a2d1b0b0c100",
  "vehicleId": "7b6e41e8-2d8b-4d83-8c90-a2d1b0b0c101",
  "problemDescription": "Проверить тормозную систему",
  "status": "Created",
  "workTotal": 0.00,
  "partsTotal": 0.00,
  "totalCost": 0.00
}
```

### Ошибки
- `CUSTOMER_NOT_FOUND` — клиент не найден;
- `VEHICLE_NOT_FOUND` — автомобиль не найден;
- `VEHICLE_OWNER_MISMATCH` — автомобиль не принадлежит указанному клиенту;
- `INVALID_REQUEST` — обязательное поле отсутствует или некорректно.

Предлагаемые HTTP-коды: `400` для некорректного запроса, `404` для отсутствующей сущности, `201` при успехе. Точная карта кодов должна быть закреплена в API при реализации.

### Таймаут и повтор
Для синхронного HTTP-запроса клиентский таймаут — 5 секунд. Автоматически повторять POST после сетевого таймаута без проверки результата нельзя: заказ мог быть создан, а ответ потерян. Для защиты от повторов можно добавить `Idempotency-Key`; это решение уточняется при реализации.

### Аутентификация
На этапе 1 схема аутентификации не выбрана. До публикации приложения вне учебного окружения доступ должен быть защищен. Для локальной разработки допустимо временно использовать API без пользовательской аутентификации, явно обозначив это ограничение.

### Версия и пример
`CreateServiceOrder v1`. Пример запроса и ответа приведен выше.

## 3. Протокол №2: добавление выполненной работы в заказ

### Инициатор и получатель
Инициатор — `ApiHost`/сотрудник; получатель — `WorkModule`.

### Назначение
Зарегистрировать выполненную работу и ее стоимость в конкретном заказе.

### Механизм и точка входа
HTTP `POST /api/service-orders/{orderId}/works`, JSON. Внутри приложения вызывается `IWorkService.AddAsync(AddWorkItemRequest, CancellationToken)`.

### Запрос

```json
{
  "name": "Замена тормозных колодок",
  "description": "Передняя ось",
  "price": 85.00
}
```

`orderId` передается в URL. Значения стоимости приведены как пример, а не как утвержденный прайс.

### Успешный ответ
HTTP `201 Created` и объект:

```json
{
  "id": "7b6e41e8-2d8b-4d83-8c90-a2d1b0b0c103",
  "orderId": "7b6e41e8-2d8b-4d83-8c90-a2d1b0b0c102",
  "name": "Замена тормозных колодок",
  "description": "Передняя ось",
  "price": 85.00
}
```

После добавления записи система пересчитывает стоимость заказа.

### Ошибки
- `ORDER_NOT_FOUND` — заказ не найден;
- `ORDER_CLOSED` — заказ в статусе, запрещающем редактирование;
- `INVALID_PRICE` — цена отрицательна;
- `INVALID_REQUEST` — отсутствует название или другие обязательные данные.

### Таймаут и повтор
Таймаут HTTP-клиента — 5 секунд. POST не повторяется вслепую: повтор может создать дубликат строки работы. При необходимости повторяемости позднее добавляется ключ идемпотентности.

### Аутентификация
Проверка права сотрудника на изменение заказа выполняется на уровне API. Конкретная схема входа пока не определена.

### Версия и пример
`AddWorkItem v1`. Пример запроса и ответа приведен выше.

## 4. Протокол №3: добавление запчасти в заказ (дополнительный)

HTTP `POST /api/service-orders/{orderId}/parts`; запрос содержит `partId`, `quantity` и `unitPrice`. Система проверяет, что `quantity > 0`, цена неотрицательна и заказ допускает изменение. Цена единицы фиксируется в записи заказа. После успешного добавления пересчитывается стоимость заказа. Коды ошибок: `ORDER_NOT_FOUND`, `ORDER_CLOSED`, `PART_NOT_FOUND`, `INVALID_QUANTITY`, `INVALID_PRICE`.

## 5. Изменение статуса заказа (дополнительный)

HTTP `PATCH /api/service-orders/{orderId}/status`; запрос:

```json
{ "status": "InProgress" }
```

Операция проверяет разрешенность перехода. Ошибки: `ORDER_NOT_FOUND`, `INVALID_STATUS_TRANSITION`, `INVALID_REQUEST`. Допустимые переходы описаны в `project-scope.md`.
