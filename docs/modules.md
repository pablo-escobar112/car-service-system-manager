# Модули и ответственность

## 1. Список модулей

| Модуль | Ответственность | Основные операции |
|---|---|---|
| `CustomerModule` | Учет клиентов | Создать, получить, обновить клиента |
| `VehicleModule` | Учет автомобилей и их связи с клиентами | Зарегистрировать автомобиль, получить карточку, изменить сведения |
| `ServiceOrderModule` | Жизненный цикл заказов | Создать заказ, получить заказ, изменить статус |
| `WorkModule` | Работы, выполненные в рамках заказа | Добавить работу, просмотреть список работ, изменить запись до закрытия заказа |
| `PartsModule` | Справочник запчастей и записи об использовании | Получить сведения о запчасти, добавить запчасть к заказу с количеством и зафиксированной ценой |
| `PricingModule` | Расчет стоимости | Рассчитать сумму работ, запчастей и общий итог |
| `ApiHost` | HTTP API и входная точка приложения | Принимать HTTP-запросы, проверять входные данные и вызывать прикладные сервисы |
| `Contracts` | Общие DTO и публичные контракты | Содержит типы запросов/ответов, используемые между модулями |

Это логические границы. На первом этапе они не означают, что каждый модуль обязательно будет отдельным исполняемым сервисом. Предполагается единое приложение с модульной структурой.

## 2. Ключевые правила

- `ApiHost` не должен содержать бизнес-правила расчета цены или переходов статуса.
- `PricingModule` рассчитывает итог из строк заказа; он не должен самостоятельно менять статус заказа.
- `ServiceOrderModule` координирует заказ и контролирует допустимые переходы статуса.
- `WorkModule` и `PartsModule` не должны обращаться к приватным внутренним классам друг друга.
- Общие модели передачи данных располагаются в `Contracts`.
- Доступ к хранилищу скрывается за репозиториями/сервисами соответствующих модулей; конкретный паттерн можно уточнить на этапе реализации.

## 3. Основной сценарий

1. Приемщик регистрирует клиента или находит существующего.
2. Приемщик регистрирует автомобиль клиента или выбирает существующий.
3. Создается заказ со статусом `Created`.
4. Механик добавляет выполненные работы.
5. Механик/приемщик фиксирует запчасти и количество.
6. `PricingModule` рассчитывает стоимость работ, запчастей и общую сумму.
7. Заказ переводится в `Completed`, а после выдачи автомобиля — в `Issued`.

## 4. Сценарии ошибок

- Клиент или автомобиль не найден — заказ не создается.
- Автомобиль не связан с выбранным клиентом — операция отклоняется.
- Количество запчасти меньше или равно нулю — запись не принимается.
- Цена работы или запчасти отрицательна — запись не принимается.
- Заказ закрыт — изменение состава работ/запчастей запрещено либо требует отдельного согласованного процесса.
- Недопустимый переход статуса — возвращается ошибка доменного правила.
