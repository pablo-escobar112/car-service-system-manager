# Назначение и границы проекта

## 1. Назначение

Система управления автосервисом предназначена для централизованного учета клиентов, принадлежащих им автомобилей и заказов на техническое обслуживание и ремонт. Сотрудник автосервиса должен иметь возможность фиксировать перечень выполненных работ и использованных запчастей, рассчитывать стоимость заказа и изменять его состояние.

## 2. Роли пользователей

На этапе проектирования предполагаются следующие роли:

- **Администратор/приемщик** — регистрирует клиентов и автомобили, создает заказ, фиксирует данные и меняет состояние заказа.
- **Механик** — просматривает назначенные заказы и регистрирует выполненные работы и использованные запчасти.
- **Клиент** — в базовом объеме является субъектом учета; самостоятельный личный кабинет не входит в минимальный объем первой версии.

Разграничение прав и аутентификация пользователей уточняются при реализации API.

## 3. Основные сущности предметной области

- Клиент (`Customer`);
- Автомобиль (`Vehicle`);
- Заказ на обслуживание (`ServiceOrder`);
- Выполненная работа (`WorkItem`);
- Запчасть (`Part`);
- Запись об использованной запчасти (`OrderPart`);
- Состояние заказа (`OrderStatus`).

## 4. Функциональные требования

1. Система хранит имя/наименование клиента и контактные данные.
2. Система хранит сведения об автомобиле: марка, модель, регистрационный номер и год выпуска (если известен).
3. Автомобиль связан с одним клиентом-владельцем в рамках текущей модели.
4. Сотрудник может создать заказ на обслуживание для зарегистрированного автомобиля.
5. Заказ содержит описание проблемы, даты создания и текущий статус.
6. В заказ можно добавить одну или несколько выполненных работ с названием/описанием и стоимостью.
7. В заказ можно добавить использованные запчасти с количеством и ценой за единицу на момент добавления.
8. Система рассчитывает стоимость работ, стоимость запчастей и итоговую стоимость заказа.
9. Сотрудник может изменить статус заказа только по допустимому переходу.
10. Система позволяет просмотреть заказ вместе с автомобилем, клиентом, работами и запчастями.

## 5. Границы первой версии

### Входит в проект

- учет клиентов и автомобилей;
- создание и просмотр заказов;
- регистрация выполненных работ;
- регистрация использованных запчастей в рамках заказа;
- расчет стоимости заказа;
- управление статусом заказа;
- базовое HTTP API и хранение данных.

### Не входит в минимальную версию

- онлайн-оплата и банковские интеграции;
- интеграция с поставщиками и автоматический заказ запчастей;
- SMS/e-mail уведомления;
- мобильное приложение;
- бухгалтерский и налоговый учет;
- складская инвентаризация с закупками и списанием вне заказов;
- интеграция с внешними каталогами автомобилей;
- полноценный портал клиента.

Эти функции могут рассматриваться как расширения, но не должны считаться реализованными в рамках минимальной версии.

## 6. Правила расчета стоимости

Для первой версии используются следующие правила:

- стоимость работы задается для каждой записи работы;
- стоимость использованных запчастей равна `количество × цена за единицу`;
- итоговая стоимость заказа равна сумме стоимости всех работ и всех использованных запчастей;
- денежные значения представляются типом `decimal`, а не `float`/`double`;
- цена запчасти фиксируется в заказе на момент добавления, чтобы последующее изменение справочной цены не меняло стоимость уже оформленного заказа;
- скидки, налоги и оплата не входят в базовый расчет, пока это отдельно не согласовано.

## 7. Жизненный цикл заказа

Предлагаемые статусы:

`Created` → `InProgress` → `WaitingForParts` (при необходимости) → `Completed` → `Issued`.

Также до начала работ может быть установлен статус `Cancelled`.

Недопустимые переходы должны отклоняться. Например, завершенный или выданный заказ нельзя снова перевести в `InProgress` обычной операцией изменения статуса. Правила переходов будут покрыты тестами при реализации.

## 8. Допущения и риски

- На этапе 1 не выбран способ аутентификации; API сначала проектируется для учебного окружения.
- Не определено, могут ли у автомобиля быть несколько владельцев в истории; первая версия хранит текущего владельца.
- Не определены правила округления валюты и налоговые требования; до их уточнения сумма хранится как `decimal` с двумя знаками после запятой в отображении.
- Не определено, требуется ли складской остаток запчастей; в первой версии учитываются запчасти, использованные в заказе, но полноценный склад не обещается.
