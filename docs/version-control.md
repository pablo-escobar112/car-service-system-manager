# Правила ведения репозитория

## 1. Ветвление

Для этапа 1 используется рабочая ветка `docs/project-artifacts`. После согласования этапа изменения публикуются в GitHub отдельным набором коммитов.

В последующих этапах предполагаются ветки вида:
- `feature/<short-name>` — новая функциональность;
- `fix/<short-name>` — исправление дефекта;
- `docs/<short-name>` — документация.

## 2. Коммиты

Коммиты должны отражать одну логическую группу изменений. Рекомендуемый стиль сообщений:

- `docs: define project scope`
- `docs: describe modules and architecture`
- `docs: define module contracts`
- `docs: add testing strategy`
- `docs: add architecture decisions`

Не следует включать в один коммит несвязанные изменения.

## 3. Перед началом работы

```bash
git status
git branch --show-current
git log -1 --oneline
```

Если репозиторий еще не содержит коммитов, `git log -1` сообщит, что коммитов нет; это нормально для пустого репозитория.

## 4. Перед публикацией

```bash
git diff --check
git status
git diff --stat
```

Убедитесь, что в репозиторий не попали пароли, токены, локальные настройки IDE, файлы сборки и личные данные.

## 5. Публикация

После создания первого коммита и настройки ветки изменения отправляются в репозиторий GitHub. Для пустого удаленного репозитория может потребоваться первая отправка ветки с `-u`. Точные команды зависят от фактической текущей ветки и состояния GitHub-репозитория; перед выполнением их нужно проверить.

## 6. Доказательства этапа

В отчете должны быть реальные выводы команд и ссылка на опубликованный коммит. Не записывайте тесты или сборку как успешные, если они не запускались.
